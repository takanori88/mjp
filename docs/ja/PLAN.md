# mjp Phase 1 調査・設計計画

[English](../en/PLAN.md)

調査日: 2026-10-06

対象: macOS Apple Silicon。実装はこの計画の後に開始する。

2026-10-08 に名称を `mdq` から `mjp`（Markdown. Just Preview.）へ変更した。既存の Homebrew formula が `mdq` コマンドを使っているため、CLI・パッケージ・アプリ識別子も統一する。GitHub のリポジトリ名も `mjp` に変更し、履歴は維持する。以下の設計・計測前提は変更しない。この文書には、後続の実装判断も注記している。

## 1. 要件と完了条件

`mjp <file>` でMarkdownを一つだけ開き、GUIの終了を待たずにCLIはシェルへ戻る。`Esc` は検索の状態に応じて、開いている検索の取消、確定後の印の消去、プレビューの終了を行う。Phase 1はエディタやファイル管理機能を持たない。

| 領域 | Phase 1 の要件・判定 |
| --- | --- |
| CLI | 相対・絶対パスを受け付け、正常時はGUIを表示したままプロンプトを戻す。ファイルの複数指定・存在しないファイル・ディレクトリ・読めないファイルはGUI起動前に標準エラーへ理由を出し、非0で終了する。Markdown以外の拡張子もテキストとして試みる（拡張子で拒否しない）。UTF-8で読めない場合は明確にエラーにする。 |
| 表示 | CommonMarkとGFMの見出し、段落、強調、取り消し線、リンク、引用、リスト、タスクリスト、表、インラインコード、コードブロック、水平線を表示する。長文と横長の表・コードをスクロールできる。 |
| コード | 主要言語のfenced codeを色分けする。未知の言語はエスケープ済みプレーンテキストとして表示する。 |
| 見た目 | 既定ではOSのLight/Darkに自動追従し、テーマ設定で固定できる。本文幅、行間、見出し階層、コード・表の可読性を優先する。ツールバー、サイドバー、タブ、設定UIは作らない。 |
| 更新 | 対象ファイルの保存を検出し、自動再描画する。削除・読み取り失敗時はウィンドウ内に小さなエラーを表示し、復旧後に再表示する。可能ならスクロール位置を維持する。 |
| 終了 | `Esc` は開いている検索を取り消す。検索欄が閉じていれば表示中の印を消し、印がなければ現在のウィンドウを閉じる。検索入力欄の外の `q`、macOSの`Cmd+W`、通常の閉じる操作は直接現在のウィンドウを閉じる。ウィンドウと未完了のオープン要求がなくなると終了し、macOSの`Cmd+Q`はプロセス全体を終了する。将来のWindows/Linuxでは`Ctrl+W`も扱う。 |
| 性能 | 起動時間を実測して記録する。正式な閾値は実機の初回測定後に設定し、改善の優先順位を機能追加より高くする。 |

Phase 1で扱わない機能は[PROJECT.md](PROJECT.md)の第6・7・12・14節に従う。特にMermaid、KaTeX、CLIでの複数ファイル引数、配布自動化は後続段階とする。Finder要求では後述のとおり複数ファイルを別々のプレビューで開ける。単発の標準入力には後述のとおり対応する。画像は当初の最低限の表示項目には含めなかった。現在はMarkdownの閲覧用途として、後述するローカルのラスター画像に対応する。外部画像と生のHTMLは引き続き対象外とする。

後続のUX判断として、最小限のVim風キー操作はQuick Lookの閲覧と終了をマウスなしで完結させるために採用し、編集やモード管理には広げない。

## 2. 公式仕様の確認と技術選択

### Tauri 2

- Tauri 2はRustのアプリ本体とOSのWebViewを組み合わせる。macOSの`.app`には実行ファイルが`Contents/MacOS`に入るため、文書化したCLIのインストールでは単体実行ファイルを `~/.local/bin` へコピーする。開発中は生成された実行ファイルを直接呼んでCLI動作を検証する。出典: [Tauri Architecture](https://v2.tauri.app/concept/architecture/)、[macOS Application Bundle](https://v2.tauri.app/distribute/macos-application-bundle/)。
- Tauri 2のCLIプラグインは位置引数を扱える。ただし単一のパスだけならRustの`std::env::args_os`で十分で、追加プラグインとJS側の引数取得を省ける。非UTF-8のOSパスも`OsString`として受け取り、ファイル読込時に処理する。`--help`と`--version`の必要性は最小CLIとして実装時に決める。出典: [CLI plugin](https://v2.tauri.app/plugin/cli/)。
- 設定上のウィンドウは`create: false`にでき、検証後だけRust側で作成できる。これによりエラー時に空のウィンドウを出さずに済む。出典: [Tauri Configuration](https://v2.tauri.app/reference/config/)。
- Rustからフロントエンドへの変更通知はイベント、フロントエンドからの本文取得は限定したコマンドで行う。読み込みの主体をRustにまとめる。出典: [Calling Rust from the Frontend](https://v2.tauri.app/develop/calling-rust/)。
- アプリのコマンドをビルド時のマニフェストに宣言し、各 `preview-*` ウィンドウには使用する4コマンドを許可する。`perf`機能では計測コマンドと別サブディレクトリのcapabilityを追加で選択する。通常ビルドはそのcapabilityを除外し、以前の計測ビルドが生成した計測用permissionも削除する。同じチェックアウトでビルド方式を切り替えても設定が再現できるようにするためである。フロントエンドに公開するリンク処理は引き続きRustのopenerラッパーに限定する。
- デバッグ時のナビゲーションには`build.devUrl`のoriginを使い、開発サーバーのアドレス変更にRust側の修正を不要とする。この許可はdebug assertionsが有効な場合だけコンパイルし、同梱ページのナビゲーションは変更しない。
- WebViewの権限はcapabilitiesで絞り、CSPは設定しない限り有効にならない。ファイルシステム・shell等の汎用プラグインをフロントエンドに与えない。出典: [Capabilities](https://v2.tauri.app/security/capabilities/)、[CSP](https://v2.tauri.app/security/csp/)。

### Markdownレンダラ候補

| 候補 | 利点 | 懸念 | 判断 |
| --- | --- | --- | --- |
| [Marked](https://github.com/markedjs/marked) | GFMが標準で有効。タスクリスト・表を含め、単一のレンダラで実装しやすい。 | 出力HTMLを無害化しないため、別のサニタイザが必須。 | **採用候補**。GFMの網羅と単純さを優先。 |
| [markdown-it](https://github.com/markdown-it/markdown-it) | CommonMark準拠で高速。HTMLは無効化でき、表・取り消し線も扱える。 | GFMタスクリスト等には追加プラグインが必要。 | Markedで性能・互換性に問題が出た場合の代替。 |
| [remark-parse + remark-gfm](https://github.com/remarkjs/remark-gfm) | GFMを明示的に組み込め、AST拡張に強い。 | HTML化まで複数パッケージと処理段階が必要。 | 今回の単純なviewerには過剰。 |

当初の採用候補は Marked だったが、実装後に大きな文書の変換が遅いことが分かり、現在は `markdown-it` と task list プラグインを使用している。測定と変更理由は [PERFORMANCE.md](PERFORMANCE.md) に記録した。

MarkedのGFM既定値とサニタイズに関する仕様: [Marked Options](https://marked.js.org/using_advanced)、[Marked README](https://github.com/markedjs/marked)。

### シンタックスハイライト候補

| 候補 | 利点 | 懸念 | 判断 |
| --- | --- | --- | --- |
| [highlight.js](https://github.com/highlightjs/highlight.js) | coreと必要言語だけを読み込める。同期的に処理できる。 | すべての言語を登録するとバンドルが増える。 | **採用候補**。最初はJS/TS、JSON、Python、Rust、Shell、HTML/CSSなどに限定し、実測で調整。 |
| [Shiki](https://shiki.style/guide/install) | VS Code系の文法・テーマに近い。 | テーマ・言語・WASMの読み込みが初回表示に影響しうる。 | Phase 1では採用せず、品質差が大きい場合に再評価。 |
| [Prism](https://github.com/PrismJS/prism) | 軽量な基本構成を組める。 | 言語管理と見た目の調整が別途必要。 | highlight.jsとの実測比較が必要な場合のみ検討。 |

言語はコードフェンスで指定されたものだけをハイライトし、自動言語判定は使わない。未知の言語は安全にエスケープして表示する。Light/Dark用のハイライト色はアプリに同梱する。CDNには依存しない。

ハイライトしたコードには専用のDOMPurify設定を使い、テキストとハイライト用クラスを持つspanを保持する。入れ子のスコープと埋め込み言語のクラスも対象とする。変換をハイライターの差し替えができる小さな関数に分離し、通常の色分けと許可する出力構造を独立して検証できるようにする。DOMテスト用のjsdomは開発時だけ使用し、アプリは引き続きWebViewのDOMを使う。

Markdownとして描画する入力はUTF-8で128 KiBまでとする。解析前に判定し、これを超える文書は既存の10 MiBのファイル上限まで、全文をプレーンテキストで表示して案内を出す。バイト数による上限は判定が軽く、Markdownの構造に依存しない。[PERFORMANCE.md](PERFORMANCE.md)の3種類の入力について、測定したMacで初回表示2秒以内を目標とする。すべての文書・機種での保証ではない。本文が変わったかどうかとは独立して通知を更新し、読み取りエラーと監視の警告をプレーンテキスト表示の案内より優先する。今回の変更ではIPCスナップショットの形式を維持する。

### フェンス付きコードのコピー

既存の Markdown レンダラーでフェンスのトークンに識別属性を付け、サニタイズとハイライトの後に DOM API で標準のボタンを追加する。言語未指定のフェンスとインデント式コードを区別し、パーサーの通常のエスケープを維持する。操作部分は `pre` と `code` の外側、横スクロールするコードの右隣の細い列の上端に置く。コードと同じ行に配置して従来の上余白を保ち、操作用の列を確保することで長い行も横スクロール中にボタンに隠れないようにする。アイコンとツールチップで結果を伝え、結果表示の行は追加しない。SVG アイコンは GitHub の Octicons のパスデータを埋め込んで DOM API で生成し、アイコン用の依存を追加せずに GitHub のコピー操作と見た目を揃える。MIT の表示は [THIRD_PARTY.md](THIRD_PARTY.md) に記録する。文書の本文をコピーするときにツールチップや状態通知の文言が混ざらないよう、操作部分はテキスト選択の対象外とする。`code.textContent` をトリミングせずコピーし、表示中の空白とパーサーが正規化した改行を保持する。タブと改行以外の制御文字と、その他の既定で無視される文字は除き、読者が見た内容だけをクリップボードに入れる。除いたことは結果に表示する。結合用の文字、異体字セレクター、双方向テキストの書式指定は、絵文字やペルシア語・インド系の文字、漢字の異体字、右から左へ書くテキストの表示が変わるため残す。埋め込み・上書き・分離の制御文字があると表示上の順序とコピーされる順序が食い違いうるため、コピー内容を書き換えるのではなく、それらを含むコードブロックの上に短い注意書きを出す。これはコードホスティングサービスやエディタの一般的な扱いに合わせたもので、表示時に知らせることでボタンを使わず手で選択する読者にも届く。インラインコードと大きなファイルのプレーンテキスト表示は従来どおりとする。

テキスト書き込み関数をプレビューブリッジから渡し、ボタン操作中に直接 `navigator.clipboard.writeText` を呼ぶ。WebView の API を利用し、実行時依存やクリップボード読み取り権限を追加しない。API が使えない場合や書き込みが拒否された場合は失敗を表示する。2026-10-21 に、独立した macOS の WKWebView 検証プログラムで本番用フロントエンドを `tauri://localhost` から読み込み、Tauri の文書取得ブリッジをスタブに置き換えて確認した。ネイティブのクリック・Enter・Space のそれぞれで、タブ・日本語・記号・末尾改行を含む本文がシステムのクリップボードと一致した。幅 800 px のライト表示と幅 360 px のダーク表示も、以前の線画アイコンで目視確認した。Octicons のアイコンと GitHub のツールチップ色は、この検証プログラムでまだ確認していない。これはフロントエンドと WebView の経路の検証であり、パッケージ化した Tauri アプリ全体や VoiceOver の読み上げの検証ではない。

ボタンのアクセシブル名はブロック番号を含む固定の名前とし、視覚的に隠したブロックごとの polite ライブリージョンで処理中・結果を通知する。アイコンボタンは枠線なしとし、キーボードフォーカスの輪郭線は残す。ツールチップはボタンの左側に、ホバー時は200ミリ秒待ってから表示し、キーボードフォーカスやコピー操作中は即時表示する。失敗後も含め、ホバーとフォーカスが外れたら即座に隠し、ツールチップがコードに重なったまま残らないようにする。エラーアイコンは次の試行まで残し、失敗はライブリージョンで通知する。ツールチップの色はライト・ダークとも GitHub の Primer の強調色に合わせる。成功時は緑のチェックマークを2秒間表示してから、コピーアイコンへ戻す。新しい試行では前回の復帰タイマーを取り消し、文書の置き換えやページ終了時にはすべてのタイマーと保留中の処理による表示更新を停止する。処理中の再操作は `aria-disabled` とハンドラーで抑制し、フォーカスを維持する。ファイルエラーの表示とは分離する。DOM テストは書き込み関数を差し替え、システムのクリップボードを使わずコピー・失敗・再試行・文書の置き換えを確認する。

### ローカル画像

生のHTMLは引き続き無効にし、Markdownの画像記法に対応する。パーサーは読み込みを起こさない仮の表示要素を出力し、`get_image` がTauriのバイナリ応答でラスター画像を返した後にフロントエンドで画像要素を作る。汎用ファイル配信プロトコルを公開せず、文書中のURLを画像の参照先へ直接設定しないためである。PNG・JPEG・GIF・WebPの識別子からMIME型を選び、デコードはWebViewで行う。読み込みやデコードに失敗した場合は代替テキストを残す。

読み込み範囲は `.git` のある最も近い親ディレクトリとし、見つからない場合はMarkdownを含むディレクトリとする。翻訳文書から親相対パスでリポジトリ内の画像を共有できるようにしつつ、任意の絶対パスは受け付けない。Unixでは範囲のディレクトリを開いたまま保持し、正規化した相対パスを `openat` と `O_NOFOLLOW` で一要素ずつたどる。途中の要素はディレクトリ、最後に開いたファイルは通常ファイルであることを確認する。範囲内を指すものも含め、シンボリックリンクは扱わない。他のOSでは同等の範囲制限付き読込を実装してから画像を有効にする。

画像1つの読み込みには既存のファイル上限と同じ10 MiBを使い、読み込み中に大きくなる場合も上限付きで読む。本文の描画後に画像を順番に取得し、同じ参照先ではBlob URLを共有する。文書の置換とページ終了時にはURLを解放し、置換後に完了した古い取得結果は表示しない。1回の描画につき画像記法は64個、重複を除く符号化済み画像データは合計32 MiBまでとし、合計上限に達したら新しい参照先の取得を止める。これは転送量・保持量の制限であり、デコード時間や展開後の画素メモリ量を保証するものではない。初回実装では画像単独の保存を監視せず、プレビューを閉じてから開き直したとき、またはMarkdown本文の変更時に再読込する。大きい文書のプレーンテキスト表示では画像を読み込まない。

### 表示中の文書内検索

文書内検索（Issue #34）は、Markdown・プレーンテキストのどちらでも、1つのプレビューの描画後の文字列を対象とする。既存のVim風の閲覧キーに揃え、`⌘F` または `/` で一時的な検索欄を開き、入力欄のEnterで確定してから `n`／`N` で移動する。確定後は検索欄を隠し、本文を中心に読み続けられる最小のUIとする。入力欄では閲覧キーを文字入力に使え、IME変換中のEnter／Escは変換操作に任せる。正規表現、単語単位の一致、置換、履歴、複数ファイルの横断検索、`?` による後方検索は対象外とする。操作は [README](README.md#文書内検索) に記す。

全一致と現在の一致は、本文の兄弟コンテナに色付きの箱を重ねて示し、本文ノード、シンタックスハイライト、コピーボタン、リンク操作を保つ。CSS Custom Highlightの背景はWebKitで再描画の端に帯が残り、行ごとの高さもそろわないため不採用とし、文字色と下線も実機で見つけにくいと判断されたため採らない。重ね描きはCSS.highlightsへの登録にもSelectionによる代替表示にも依存しない。ブロック境界、リスト項目、表のセル、明示的な `br`、除外する部分木で区間を区切る。区間内のインライン要素はまたいで一致し、これらの区切りはまたがない。`pre` の外では、ノード境界をまたぐ U+0020・タブ・LF・CR の連続を空白1つに縮約し、区間の前後の空白を除く。NBSP と U+3000 はそのまま残す。`pre` 内は空白と改行を保持する。縮約した空白は、ノードをまたぐ始点・終点を含めた元の空白列全体に対応させ、レイアウトがどの部分を表示しても Range で覆う。特に10 MiBのプレーンテキストノードでは、文字ごとの対応表ではなく連続するテキストの範囲を保持する。コードの操作部分、文字方向の注記、検索欄は収集対象外とする。

U+FF01–FF5E を先にASCIIへ変換し、その後UTF-16の各単位を、結果が1単位の場合だけ小文字へ変換する。サロゲートと、U+0130のように小文字化で長さが増えるものはそのまま残す。これによりDOMのオフセットを変えずに `Ａ`、`ａ`、`A`、`a` を同一視できる。NFKCは広い互換文字の置換と長さの変化を伴いうるため使わない。ひらがな・カタカナの同一視も、大文字・小文字と全角・半角の対応を超えて別の文字列まで一致させるため採らない。

ローカル画像の仮表示部分（`[data-mjp-image]` 配下）とその代替テキストは、読み込みの成功・失敗によらず検索から除外する。非同期の画像への置き換えで検索結果を変えないためである。外部画像と画像数の上限を超えた参照は、レンダラーが通常の本文として出力したテキストのまま残るため検索対象に含める。

文書順で重ならない一致を**1000件**まで保持し、対応するRangeを作る。1001件目が見つかったときだけ打ち切りフラグを立てる。ちょうど1000件なら `3/1000`、超えた場合は `3/1000+` と表示し、保持した一致の範囲で巡回する。検索欄を開いている間は0件の `0/0` も含めて欄内に表示し、確定後は行末に `[3/1000+]` のようなバッジを表示する。一致がなくなればバッジを隠す。上限で抑えるのは一致位置の保持量とRange生成であり、区間の収集や、一致なし・少数一致で必要な全文走査ではない。

1000件の上限は、2026-11-01にmacOS arm64上のNode v24.22.1とjsdom 30.1.3で行った計測に基づいて選んだ。10 MiBのプレーンテキストと128 KiBのMarkdownについて、一致なし、10件の一致、`a` の反復を `a` で検索するASCIIの入力を使った。Markdownは見出し、強調、リンク、リスト、表、コードを含む505区間で、反復時は125,695件の一致となる。各条件は新しいDOM複製を文書に接続し、描画と準備を時間に含めず、ウォームアップ2回と計測7回を実行した。反復時のRange生成時間の中央値は次のとおりだった。

| 入力 | 1000件のRange | 10000件のRange | 100000件のRange |
| --- | ---: | ---: | ---: |
| 10 MiB プレーンテキスト | 2.12 ms | 12.97 ms | 110.51 ms |
| 128 KiB Markdown | 2.41 ms | 13.93 ms | 109.42 ms |

箱の配置と描画の余裕を残すため、1000件を保持する。区間の収集と畳み込みはプレーンテキストで約6.7〜6.9 ms、Markdownで約17.0〜18.6 ms、一致なし・10件一致の走査は最大約0.3 msだった。本文ノードが変わるまで区間と畳み込み済み文字列をキャッシュし、入力ごとの再収集を避ける。これらは箱の配置・レイアウト・描画を含まないjsdomの数値であり、WKWebViewの操作遅延や起動時間の基準を保証するものではない。

#### 検索の状態と移動

検索欄の表示と印の表示を分けて保持する。閉じた状態から開くときだけ `origin = { scrollY, query, index, shown }` を保存し、開いた検索欄への再フォーカスでは上書きしない。開くときと検索語を変えたときには、Range上端の文書座標が `origin.scrollY` と上部の遮蔽の高さの合計以上になる最初の一致を選ぶ。遮蔽は状態バナーと検索欄との横方向の重なりを考慮し、後ろに一致がなければ先頭へ巡回する。開いたときはスクロールを要求せず、入力時に選んだ一致を表示する。検索によるスクロール後も入力の起点を元の閲覧位置に保ち、既存の検索語で開き直した場合も、未編集のEnterより前に新しい起点から選び直す。

EnterはShift+Enterも含めて予約中の検索を完了させ、現在の一致から移動せず確定する。検索欄を閉じて印を残し、必要なら一致を表示して起点を消し、`preventScroll` で本文へフォーカスを戻す。空でない検索語が0件の場合は `0/0` のまま編集可能にし、取消用の起点も保持する。空の検索語では検索欄を閉じて印を隠す。`commit()` はそれぞれ `"committed"`、`"empty"`、`"closed"` を返し、プレビュー側は欄が実際に閉じた場合だけ「開く意図」を解除する。

Escでの取消は、予約中の検索を取り消してから起点の検索語を戻し、これを新しい検索語への変更とは扱わず、現在の本文に対して結果を作り直す。起点の一致番号が範囲内なら維持し、それ以外は最初の一致へ戻す（0件なら番号なし）。印の表示と保存したスクロール位置を戻し、欄を閉じてフォーカスを戻し、起点を消す。検索中の本文置換、再度の `⌘F`、0件で確定しなかった場合にも対応する。欄が閉じているときのEscは、表示中の印とバッジを消して検索語と一致番号を保持し、次のEscでウィンドウを閉じる。印が既に隠れていれば最初のEscで閉じる。入力欄の外の `q` と `⌘W` は印の表示に関係なく直接閉じる。

`n`／`N` では、先に現在の本文で結果を最新にする。現在の一致が縦方向にすべて画面内に収まり、遮蔽されていなければ、前後へ巡回する。それ以外では、`n` は上端が閲覧範囲の上端以降にある最初の一致、`N` は下端が閲覧範囲の下端以前にある最後の一致を選び、なければ先頭／末尾へ巡回する。スクロールで読み進めた位置から検索を再開するためである。検索欄を開かず、印とバッジを再表示する。本文の置き換えでは範囲内の番号を維持し、それ以外は最初の一致へ戻し、検索によるスクロールを要求しない。区間と結果の古さを別々に管理し、予約中の入力は本文置換時の再検索に吸収する。同一本文と古いrevisionでは結果を無効化しない。

検索モジュールは最初の操作で動的に読み込み、起動経路にUIの生成や本文の収集を加えない。ビルドでも検索は別チャンクとなる。読み込みと初期化のPromiseを共有し、最後の開閉の意図だけを反映する。入力の検索は `requestAnimationFrame` でまとめる。Rangeの矩形から状態バナー、検索欄、コード・表の横スクロールを考慮して一致を表示する。一致が閲覧範囲の中央半分の外にあるか、隠れているか、画面外にある場合は、縦方向の中央へスクロールし、中央半分の内側にある一致ではスクロールしない。画面外だけでなく端に近い一致も中央へ寄せるのは、一致が最下行に来たときにも前後の行を読めるようにするためであり、中央半分の帯を設けるのは、近くの一致間の移動で画面が揺れないようにするためである。ページ終了時には処理を取り消して印を除き、破棄後に読み込みが成功・失敗しても表示を更新しない。

本文には確定・取消後の閲覧キーを受けるため `tabIndex=-1` を設定する。Tabの移動先ではない閲覧面として、輪郭線の抑制は `#document:focus` に限定し、ボタンやリンクのフォーカス表示を保持する。WebKitのフォーカスリングの見た目はTDD例外となるGUIの検証項目とする。

#### 一致の箱の重ね描き

本文の前に `aria-hidden` の `search-marks` コンテナを置き、ポインター操作とテキスト選択の対象外にする。一致ごとに `Range.getClientRects()` の幅・高さが0でない矩形につき1つの箱を作り、`scrollX`・`scrollY`を足したページ座標に配置する。ウィンドウのスクロールでは本文と一緒に動くため再計算しない。コードブロックや表など、入れ子を含む横スクロール要素すべての見えている矩形で切り取り、完全に外れる箱は省く。矩形を読み取ってから箱を使い回し、DocumentFragmentで1回の追加にまとめ、本文のclass・style・内容・構造を変えない。

ほかの一致は `#ffed99`、現在の一致は `#ffb347` とし、現在の箱を上に重ねる。ライトでは箱全体をmultiply合成し、重なった通常の箱を現在の箱で置き換えてから本文と合成する。ダークでは同じ色をalpha 0.35と0.55で通常合成し、メディアクエリに直接指定する。矩形と現在位置の更新は、検索欄を開いている間もバッジと同じフレームにまとめる。検索の消去と0件では箱を取り除いて配置予約を取り消し、取消では検索前の印の表示状態へ戻す。破棄時にはコンテナを取り除き、保持した箱も解放する。

#### 行末の件数バッジ

`createElement` と `textContent` で `span.search-count` を本文の兄弟として作り、文書座標で絶対配置して本文と一緒にスクロールさせる。`[index+1/件数]` を表示し、上限超過なら `[3/1000+]` とする。`aria-live="polite"` を付け、本文より小さい控えめな文字とライト・ダークに追従する背景を使い、選択不可・ポインター透過とする。検索欄が開いている間、印が隠れているとき、一致がなくなったとき、破棄後には隠す。

一致のRangeの最後の矩形を基準行にする。`pre` 内では、一致の終点から次のLFの直前、なければ区間の末尾までのテキストRangeを、ノードをまたぐ場合も区間の対応表で求め、最後の矩形の右端を行末とする。`pre` の外では、一致の終点から区間末尾までを測り、基準行と縦に重なる矩形の右端の最大値を使う。残りのRangeに矩形がなければ一致の右端を使う。本文より広い箱を返しうるブロック全体の矩形や、文書全体に負荷が比例する `pre` 全体の計測は避ける。行末の8 px右、基準行の上端に配置し、収まらなければ本文右端の内側に右寄せして重ねる。横スクロールするコード・表では、表示されている内側の右端も境界に使う。

再配置は再検索と分け、最新の一致の矩形を使って箱とバッジの更新を共通の `requestAnimationFrame` で1フレームに1回へ集約する。確定、移動、取消で印を復元したとき、表示中の結果の本文置換、ウィンドウのresize、本文と状態バナーへの `ResizeObserver`、本文でcaptureするscroll・load・errorを契機とする。画像のload/errorも使うのは、本文が `min-height: 100vh` のため、監視しているサイズが変わらなくても一致行が動く場合があるためである。予約した処理は印が表示中かつ未破棄の場合だけ適用し、バッジには欄が閉じている条件も加える。ページ終了時には予約を取り消し、observerとリスナーを解除する。

#### 行末計算の計測

2026-11-01にApple M1 Max、macOS arm64、Node v24.22.1、jsdom 30.1.3で、10 MiBのASCIIプレーンテキストの行末計算を測った。LFを含めて80 Bと4096 Bの行を反復する入力と、LFのない10 MiBの単一行を使い、文書の先頭・中央・末尾付近に3文字の一致を置いた。区間収集とバッジの配置は時間に含めず、レイアウトを計算しないjsdomでは `getClientRects()` に固定値を与えた。各条件20回のウォームアップ後、100回の呼び出しを9組測り、各組の前に計測時間外でGCした。表は各組の所要時間を100で割った値の中央値（ms/回）である。

| 10 MiB内の行幅 | 先頭付近 | 中央付近 | 末尾付近 |
| --- | ---: | ---: | ---: |
| LF込み80 B | 0.00366 ms | 0.00192 ms | 0.00199 ms |
| LF込み4096 B | 0.00248 ms | 0.00231 ms | 0.00234 ms |
| LFなし10 MiBの単一行 | 0.26324 ms | 0.12879 ms | 0.00230 ms |

行を反復した入力では、10 MiB内の位置によらず、計測用Rangeは一致後の76文字または4092文字だけを覆う。改行のない単一行では残りの長さの走査が必要になる。各組のGC前のヒープ増分を100で割った値の中央値は、一時的な割当も含め約2.0〜2.3 KiB/回だった。このjsdomの計測はJavaScriptの行走査、Range生成、固定矩形の処理を対象とし、WKWebViewのレイアウト・描画・操作遅延は実機で別途測る必要がある。

#### 実機検証

重ね描きでは `CSS.highlights` や `Highlight` を調べず、検索によるSelectionも設定しない。フォーカス移動時にはユーザーによる本文の選択を保持し、`⌘C` はWebViewの通常の入力欄・本文のコピー動作に任せる。

DOMテストではPromise、フレーム、Selection、observer、画像イベント、矩形を制御し、箱の位置、切り取り、0サイズの除外、要素の再利用、現在の一致の区別、消去、再計算と、従来の検索状態・キー操作の契約を確認する。両テーマでの色の見え方とブレンド、跡が残らないこと、1000件時の体感速度、複数行と横方向に隠れた一致、狭いウィンドウでのバッジ配置、`⌘F` のメニュー処理、IME変換中のEnter／Esc、バナーなどによる遮蔽、取消時のスクロール復元、フォーカスを戻した直後の閲覧キー、本文のフォーカスリング抑制、選択の保持と実際の `⌘C`、10 MiBの操作遅延には実機確認が必要である。`VITE_MJP_PERF` の `first_render` による起動時間の比較も未計測であり、jsdomの数値と検索の別チャンク化だけでは実機の起動遅延を確かめられない。

### 代替構成との比較

macOS専用のSwiftUI + WKWebViewならネイティブ側をさらに絞れる可能性はあるが、Windows/Linuxを視野に入れた設計をやり直すことになる。Tauri 2 + Vanilla TypeScript + Viteを第一案とする。Reactは画面状態が本文・エラー・テーマ程度しかないため採用しない。Viteはビルド時だけ使い、実行時にNode.jsや開発サーバーを必要としない。TauriとWebViewの起動コストが支配的なら、フレームワークを変える前に実測して確認する。

## 3. 最小アーキテクチャ

```text
terminal: mjp README.md
  └─ Rust CLI: 引数検査 → 絶対パス化 → UTF-8読込確認 → GUIを起動して終了
       ├─ GUIプロセス: 成功時のみ最初のTauriウィンドウを作成
       ├─ 親ディレクトリを監視
       └─ 読込コマンド + 変更イベント
            └─ Vanilla TypeScript: Markdownパーサー → HTML無害化 → 本文DOMへ反映
                 ├─ highlight.js (必要言語のみ)
                 └─ CSS: OSテーマに追従
```

- macOSのリリース版では、CLIが検証済みの絶対パスで同じ実行ファイルをGUI子プロセスとして起動し、端末から切り離して終了する。GUIはウィンドウまたは未完了のオープン要求がある間動く。`tauri dev`では開発サーバーを保つため前景のまま動かす。常駐デーモン、localhostサーバー、sidecar、single-instanceプラグインは置かない。同時に2回実行した場合は独立した2つのプレビューとする。Windows/Linuxの起動方法は移植時にOS別に実装・検証する。
- 初期表示では、各WebViewが自分の変更イベントの受信準備をした後に本文を取得する。イベントと読込が重なった場合は後続の再読込を一度行い、保存内容の取りこぼしを防ぐ。ファイル全文をイベントに載せず、再読込要求だけを送る。
- Tauriのコマンド・イベントへの接続は `main.ts` に置き、その操作をプレビュー制御関数へ渡す。ネイティブウィンドウを起動せず、アプリと同じ読込・描画・キー操作・リンク処理をDOMテストで確認するためである。先行する要求が後から完了した場合も、本文とエラー通知を更新できるのは最後に開始した読込だけとする。
- フロントエンドの `Esc` は検索の状態に応じて、開いている検索の取消、確定後の印の消去、現在のウィンドウの終了要求を行う。直接終了するショートカットも同じ最小のフロントエンド処理を使う。ネイティブの閉じる操作も同じウィンドウ単位の後始末と未完了要求を含む終了判定に集め、macOSで不要なプロセスが残らないことを確認する。
- 文書ごとのウィンドウは幅約800pxとし、本文の最大幅をCSSで制限する。狭い画面では画面幅に追従する。装飾は標準タイトルバーを基点とし、起動と操作の実測前に独自タイトルバーを作らない。
- 通常クリックと修飾キー付きクリックでは、対応するリンクを引き続き既定アプリで開く。補助ボタンによるリンククリックとドロップにはプレビュー操作を割り当てない。DOMのドロップ処理は余白を含むウィンドウ全体を対象にする。Tauriのネイティブなドラッグ＆ドロップ処理は従来どおり有効に保つ。この設定はネイティブイベント処理を制御するもので、アプリがドロップを受け付けるかを宣言するものではない。

### 起動時の設定とテーマ（Issue #37、スライス1）

固定した `$HOME/.config/mjp/config.toml` の TOML を、`session::run` で GUI ウィンドウの生成前に1回だけ読む。CLI の親、help、version、不正入力の経路では読まない。`HOME` が未設定、空、相対パスなら警告なしで既定値を使う。ターミナルと Finder から同じ場所を使いやすくするため、`XDG_CONFIG_HOME` を意図的に無視し、XDG の設定仕様には準拠しない。呼び出し元で `HOME` を変えると別の場所を読む。設定と警告は変更しないアプリ状態として保持する。文書、stdin、Welcome、Failures はすべて `create_preview` を使い、後から追加するウィンドウもプロセス起動時の設定を維持する。実行中の再読み込みと CLI の `--theme` は今回の対象外とする。

通常ファイルを非ブロッキングで上限付き UTF-8 として読む関数を Markdown と共通化し、Markdown の10 MiB上限と既存の文言は維持する。設定には64 KiBの別上限を使う。ファイルなしは警告せず既定値とし、NotFound の直後に末尾だけを `symlink_metadata` で調べ、`config.toml` 自体のリンク切れを観測した場合は警告する。親のリンクは調べず、並行した置換を常に検出するとも保証しない。通常ファイルへのリンクはたどる。他の読み込み失敗は既定値と警告1件にする。

`toml::de::DeTable::parse` を `preserve_order` なしで使い、未知のトップレベル項目の警告をキーの辞書順にし、その配下のテーブルは解釈しない。重複キーを含む不正な TOML は全設定を破棄し、バイト範囲から Unicode 文字を数えて求めた行・列付きの1行の警告にする。不正なテーマだけなら system に戻し、未知の項目があっても正しい設定は適用する。parse のみの TOML 直接依存はロック済みのバージョンを再利用し、他のバージョンを変えない。

`system` はネイティブのビルダーの `theme(None)`、固定した `light`／`dark` は対応する Tauri テーマに変換する。macOS の tao は外観をプロセス全体へ適用し、全ウィンドウ共通の設定と整合する。CSS は維持する。WKWebView の本文、コードの色、スクロールバー、OS の外観変更への追従、Finder 起動には実機確認が必要であり、変換の自動テストだけでは保証しない。

元の警告を文書の状態に保持し、snapshot ごとに表示文字列を1回だけ作る。自動更新できない理由を隠さないよう、自動更新の警告を先、設定の警告を後に追加する。制御文字を除き、最大3件を ` / ` で連結し、元の件数に基づく残りを `(+N more)` で示す。1件の上限は省略時の `…` を含む Unicode 200文字とする。持ち主が承認した暫定値であり、表示の妥当性は実機で確認する。追加ごとに revision を進め、エラーを優先表示しても警告は消さない。起動前の警告で revision が進んでも計測できるよう、描画前の `lastText === null` から `first_render` を判定し、フレームのコールバックには確定した stage を渡す。

設定による起動時間の増加、実機での警告表示、既存プロセスと新規プロセスで設定の反映が異なることは、対象機で未確認である。

### 単発の標準入力

入力フラグを必須にせず、`command | mjp` と `mjp < file` を受け付ける。ファイルの明示を優先し、`mjp -` は標準入力、`mjp -- -` は名前が `-` のファイルを選ぶ。端末で引数なしなら使い方を表示し、端末で標準入力を明示した場合は対話入力を待たずエラーにする。既存の 10 MiB 上限に1バイトだけ追加して EOF まで読み、GUI 起動前にサイズと UTF-8 を検証する。空白・改行を保持し、空の文書も受け付ける。描画の 128 KiB 境界は維持する。

文書のパスを省略可能にし、監視用の仮ファイルを作らず既存の snapshot と描画経路を共有する。標準入力のタイトルは `stdin` とし、画像の参照範囲は持たせない。タイトル指定は引き続き後続の変更とし、呼び出し元の作業ディレクトリからファイル参照権限を暗黙に与えない。

標準入力向けに画像の基準ディレクトリを明示する機能（例：`--base-dir`）は、予定に入れず見送る。Markdown がファイルとして存在するなら、`mjp <file>` で画像を解決でき、ライブリロードも効く。`git show` の出力では、過去の本文に現在の作業ツリーの画像が組み合わさってしまう。リモートから取得したテキストや生成したテキストには、表示できるローカル画像がほとんどない。画像がなくても代替テキストで内容は読める。得られるものが小さいわりに、CLI の規則と、標準入力からファイルを読む新しい経路が増える。パイプしたテキストでローカル画像が必要になる具体的な使い方が出てきたときに再検討する。

エディタバッファのライブ反映（Issue #14 の段階3・4にあたる Neovim 連携とライブ更新、`--stream` 案を含む）は採用しない。`mjp <file>` は保存のたびに表示を更新し、エディタ側の自動保存で編集中の内容はほぼ反映できる。ライブ反映には文書の区切り（フレーミング）、更新の間引き、切断処理、プロセス寿命の管理、エディタ別の連携コードが必要になるが、得られる差は保存前に見えることだけである。ファイルの保存による更新に留める方が、Neovim 拡張を対象外とする [PROJECT.md](PROJECT.md) の軽さとエディタ非依存の方針に合う。ファイルとして存在しない文書を継続的に更新しながら表示したい具体的な使い方が出てきたときに再検討する。

macOS のリリース版では、検証済みの本文を匿名パイプで切り離した GUI 子プロセスへ渡す。子はウィンドウの初期化前に本文を読み、検証する。書き込み後にパイプを閉じて EOF で文書を確定し、ウィンドウの終了を待たず受け渡し後に復帰する。書き込み失敗時は子を停止して終了を回収する。本文をコマンド引数・環境変数・一時ファイルへ置かずに済む。ファイル入力は従来のパス受け渡しを維持し、開発ビルドは引き続き前景で動かす。依存物やフロントエンドの IPC コマンドは追加しない。

### 文書はウィンドウに所属する

各プレビューはプロセス内で一意な `preview-<n>` ラベルを持ち、登録表で文書と画像スコープを保持する。コマンドは注入された呼び出し元 WebView のラベルから文書を検索し、再読み込み通知もそのウィンドウだけが購読する。共通テンプレートと `preview-*` capability により、フロントエンドから文書を選ばせず、CLI と OS 経由のプレビューで同じ経路を使う。ウィンドウ生成・描画の性能マークには注入されたラベルを付け、プロセス起動のマークと区別する。


登録項目が停止可能な監視ハンドルを所有し、ワーカーは自分の文書だけを参照する。閉じる操作の取り消しができなくなる `Destroyed` で登録を解除する。ウィンドウ生成に失敗した場合も登録と監視を撤回する。監視の停止や join の前に登録表のロックを解放する。停止通知はイベント待ち・debounce 待ちを解除し、更新処理と直列化することで、閉じたプレビューへの後続更新を防ぐ。ラベルはプロセスの生存中に再利用しない。

1つのウィンドウを閉じても他のウィンドウは動作を続ける。自然終了には登録表が空で未完了のオープン要求もないことが必要で、明示的な Quit はプロセス全体を終了する。最後のプレビューで終了するのは軽い閲覧体験を優先した mjp の判断であり、ウィンドウがなくても残る一般的な文書アプリとは異なる。


### ファイルオープン要求の方針

要求元とプロセスの起動モードを分ける。CLI 初期入力の失敗は端末へ、OS オープン要求の失敗は CLI 子プロセスが受け取った場合もイベントごとに1つの案内ウィンドウへ出す。ローカルの file URL を検証し、query・fragment・パス変換失敗を拒否する。各イベントの先頭10件を処理し、超過分は読み込み失敗とまとめて案内する。10件はイベント単位の UX 方針であり、全ウィンドウ数の上限ではない。案内の詳細は10件までとし、省略件数を示す。改行と制御文字を可視のエスケープに変え、名前中のどのバッククォート連続よりも長いコードフェンスを使って、パスと理由をそれぞれ文字列として表示する。1件はパスの行と、その下にインデントした理由の行の2行にする。ファイル読み込み失敗は表示までパスと理由を別フィールドに持つ型で受け渡し、CLI エラーでは従来どおり `path: reason` に整形する。案内でのパスの重複を避け、長いパスでも理由を行の左側から読めるようにするためである。

canonicalize 後のパスで、開いた文書と処理中の予約を識別する。開いている文書は前面化し、読み込み中の重複要求は既存の読み込みにまとめる。読み込みやウィンドウ生成に失敗した場合は予約を解除し、開いた文書として登録しないため、修正後の再要求で自然に再試行できる。初回失敗には監視を付けず、正常に開いたファイルのライブリロード失敗には従来の回復可能なバナーを使う。

受付済みの要求は Ready 前のキュー内、読み込み中、結果のウィンドウまたは案内の生成完了まで未完了として扱う。キューの取り出しだけでは要求を完了にしない。起動時の Welcome 判定も自然終了を抑止する。Welcome は明示的な種別で識別し、文書ウィンドウの生成成功後だけ閉じる。読み込みの開始や失敗では閉じない。


### Finder 起動とプロセスの寿命

LaunchServices はバンドルにマージされた `Info.plist` の設定で `MJP_APP=1` を渡す。これは起動経路のヒントであり、権限の境界ではない。GUI 子を最優先し、次に明示的な CLI 引数、引数なしのアプリ起動ヒント、従来の端末ヘルプまたは stdin の順で判定する。切り離す CLI 子からはアプリ起動ヒントを除く。バンドルは `.md` と `.markdown` を `net.daringfireball.markdown` の Viewer、Alternate rank として宣言し、型の export は行わない。

Tauri を build してからイベントコールバック付きで run する。Ready 前は OS 要求の保存だけを行い、ワーカーがパスの canonicalize と読み込みを担当し、メインスレッドがパス予約・結果の登録・ウィンドウ生成・終了判定を担当する。登録表や要求のロックを保持したまま I/O・ウィンドウ操作・メインスレッドへの dispatch・await・監視の join をしない。キュー内にファイルがなければアプリ起動時に Welcome を表示し、プロセス生存中に表示中のウィンドウがない Reopen を受けると Welcome を再表示する。Cmd+W と閉じるボタンは1ウィンドウを閉じ、ネイティブの Cmd+Q／Quit は読み込み中でもプロセス全体を終了する。

LaunchServices のアプリインスタンスは文書ごとに別ウィンドウを開く。ディスパッチャと子プロセスを設けず、macOS のファイルオープン配送に合わせるためである。通常の LaunchServices 起動では既存インスタンスへの配送を期待するが、バンドル内実行ファイルを CLI として直接使うと複数インスタンスがありうる。そのため CLI 子も OS のオープン要求を受けると追加ウィンドウを開く。CLI 起動は独立のままにし、アプリへの転送や常駐の調整役を導入しない。現在の文書を差し替える案は、別ファイルを開く操作で閲覧中のプレビューを失わないよう不採用とした。

Finder 用バンドルは `/Applications`、単体 CLI は `~/.local/bin` に配置する。この2つの入口を分けて案内することで、バンドル内の CLI プロセスが唯一のアプリインスタンスであることに依存せず、LaunchServices の配送の前提を明確にする。標準アプリの設定は拡張子ごとに利用者が Finder で明示的に選ぶ。Alternate rank の宣言は Markdown 型の所有を主張せず、閲覧アプリの候補として利用可能にするためである。英日 README には同じインストール・再試行・終了の動作を記載する。

## 4. File watching

方式はRustの[notify](https://docs.rs/notify/latest/notify/) `recommended_watcher`を第一案とする。監視対象はファイルそのものではなく親ディレクトリを非再帰で監視し、対象ファイル名に関係するイベントだけを扱う。編集ソフトによって上書き・削除後の再作成・一時ファイルからの置換が異なるため、イベント種別を厳密に解釈せず、短いdebounce（初期値100〜200ms）後に対象パスを読み直す。重複イベントはまとめる。

一時的な読み取り失敗は短く再試行し、なお失敗した場合は最後の正常表示を残してエラーを示す。ファイルが復旧したら自動で消す。再描画前後のスクロール位置は絶対値をまず維持し、長さが大きく変わったときは新しい最大値に収める。監視資源は終了時に解放する。`notify`の公式資料はネットワークファイルシステムでイベントが届かない可能性を記載しているため、初回リリースの動作保証はローカルファイルとし、必要なら後続でpollingを検討する。

ファイルの識別情報を固定せず、保存後も選択したパスを追跡する。一時ファイルを元のファイルへrenameするエディタの保存方式と、削除後の再作成を両方維持するためである。種別とサイズは引き続き開いたハンドルで検査し、検査と読み取りを同じ対象に対して行う。編集可能なローカルファイルのライブプレビューに合わせた選択である。

関連イベント後の待機時間を140 ms、debounce全体の上限を700 msとする。無関係な兄弟ファイルのイベントでは待機を延長しない。最大5回分の待機時間で読み直しへ進むことで、連続保存中にも内容を更新し、書き込み途中の場合には既存の短い再試行を利用する。

Tauriの[fs plugin](https://v2.tauri.app/plugin/file-system/)にもwatch APIはあるが、今回それを使うとフロントエンドにファイルアクセス範囲・権限を追加する必要がある。Rust内で読込と監視を完結させる方が境界を小さく保てる。

## 5. セキュリティとリンク方針

1. 入力Markdownは信頼しない。Markdownパーサーが生成したHTMLを[DOMPurify](https://github.com/cure53/DOMPurify)でHTMLプロファイルと必要最小限のタグ・属性に絞って無害化してからDOMへ入れる。`script`、イベント属性、フォーム、iframe、SVG/MathML、危険なURLを許可しない。raw HTMLはPhase 1の機能として保証せず、安全なタグ以外は表示しない。現在は `markdown-it` で raw HTML を無効化している。
2. HTMLの無害化に加えて、CSPでアプリ同梱のスクリプト・スタイルとTauri IPCだけを許し、リモートスクリプト・フレーム・オブジェクト・フォーム送信を拒否する。`img-src blob:` で読み込み範囲を限定したRustコマンドの画像データを表示し、画像要素からの外部URL・data URL・file URLの読み込みは許可しない。CSPの正確な値はTauriが挿入するハッシュ/nonceとIPCソースを踏まえて実装時に検証する。
3. リンククリックはアプリ内WebViewを移動させない。`https:`、`http:`、`mailto:`だけを明示的に検査し、OS既定のアプリへ渡す。`javascript:`、`data:`、`file:`、相対リンクはPhase 1では開かない。Tauriの[opener](https://v2.tauri.app/plugin/opener/)を使う場合も、フロントエンドへ無制限のopen権限を与えず、Rust側の限定コマンドでURLを再検査する。WebViewの通常ナビゲーション・新規ウィンドウ要求もアプリ内URL以外は拒否する。
4. 汎用fs/shell/HTTP権限、外部CDN、ファイルをWebViewへ直接公開する広いasset protocol scopeは使わない。入力ファイルは10 MiBを上限とし、超えた場合は文書ウィンドウを開かずCLIエラーまたはOS要求の案内を出し、Live Reload時は前回の内容を残してエラー表示する。FIFOなど通常ファイル以外は読み込まない（ブロックを避けるためUnixでは`O_NONBLOCK`で開き、開いたハンドルで種別を検査する）。Markdown中のリンクと画像から任意ファイルを読めないことを確認する。

## 6. ディレクトリ構成

以下はアプリケーション構成の概要であり、一部の機能はさらに別ファイルへ分割している。

英語の詳細文書は `docs/en/`、対応する日本語版は `docs/ja/` にまとめ、言語ごとの配置を揃えてルートを簡潔に保つ。標準文書は引き続き英語版とする。英語の README は入口としてルートに残し、`AGENTS.md`、`CLAUDE.md`、`LICENSE` もルートに置く。

```text
<repository>/
├── README.md
├── AGENTS.md
├── CLAUDE.md
├── LICENSE
├── docs/
│   ├── en/              # PROJECT.md, PLAN.md, PERFORMANCE.md, RELEASING.md, THIRD_PARTY.md
│   └── ja/              # README.md と各文書の日本語版
├── package.json
├── index.html
├── vite.config.ts
├── src/
│   ├── main.ts          # 読込・更新・終了イベント
│   ├── render.ts        # Markdownパーサー / DOMPurify / highlight.js
│   └── style.css        # 本文、Light/Dark、スクロール
├── src-tauri/
│   ├── Cargo.toml
│   ├── tauri.conf.json
│   ├── capabilities/default.json
│   └── src/
│       ├── main.rs       # CLIの入口
│       └── lib.rs        # Tauri起動・読込・監視・リンク

```

ファイル分割は実装量に応じて増やす。UIフレームワーク、状態管理ライブラリ、ルーターは導入しない。

## 7. Phase 1 実装順と確認方法

1. **起動の縦断経路**: Tauri 2 + Vanilla TypeScriptを最小構成で起こし、`mjp <file>`のRust引数検査から単一ウィンドウにプレーンテキストを表示し、CLIを終了させる。絶対・相対パス、空・複数引数、存在しない/読めないファイル、終了コードを確認する。生成バイナリと`.app`内実行ファイルの両方で動作を試す。
2. **レンダリング**: Markdownパーサー、DOMPurify、必要言語だけのhighlight.jsを入れる。PROJECT.mdにある記法を一枚に集めた確認用Markdownで表示を確認する。未知のコード言語・長文・表・コードの横スクロールを確認する。現在のパーサーは `markdown-it`。
3. **見た目と操作**: Light/Dark、自動切替、標準タイトルバー、スクロール、`Esc`/`Cmd+W`/Closeによるプロセス終了を実機で確認する。
4. **Live Reload**: 親ディレクトリ監視とdebounceを加え、通常保存・atomic save・削除と再作成・連続保存を試す。スクロール位置の維持を可能な範囲で入れる。
5. **安全性と性能の仕上げ**: `<script>`、イベント属性、`javascript:`リンク、危険な画像URLなどを含む入力を試し、コードが実行されずWebViewが外部へ移動しないことを確認する。クリーン起動と連続起動の「コマンド開始→本文表示」、メモリ使用量、JSバンドルサイズを同一実機で複数回測る。数値を記録し、遅い箇所だけを改善する。

### Phase 1 の完了判定

自動テストでは、Rust側は実際のローカルファイルの変更通知から文書の再読込まで、フロントエンド側は変更イベントの購読からDOM更新までを確認する。いずれもアプリと同じ処理関数を使う。Tauriのイベント伝送、OSでのリンク起動、ネイティブウィンドウの終了、WKWebViewの動作にはmacOS上の結合確認が引き続き必要であり、個別のテスト成功だけで全経路の動作確認とはしない。

- `mjp README.md`でシェルへすぐ戻り、数秒の閲覧に十分な表示・終了体験ができる。
- 指定されたMarkdown/GFM記法と主要コード言語が読める。
- 保存で自動更新され、削除・置換・復旧時もウィンドウが破綻しない。
- CLIエラーはウィンドウを出さずに分かる文面と非0終了を返す。
- 悪意あるMarkdownから任意JavaScript・外部ページ遷移・任意ローカルファイル読込が起きない。
- 起動計測結果と未対応事項を記録し、次段階の判断材料にする。

## 8. リリースビルドのパス

`build:release` ではアプリケーションと依存ライブラリに Rust のソースパス置換を適用する。ホーム、Cargo、Rustup、チェックアウトの場所をビルド時に取得して一定の `/build/` 配下へ置き換え、共有する実行ファイルが開発者固有のディレクトリ構成に依存せず、ソースの位置を示せるようにする。Cargo のエンコード済みコンパイラフラグを使い、パス内の空白と環境変数で指定された既存のフラグを保持する。開発用コマンドでは通常のソースパスを維持する。

## 9. ソース配布

初回の公開対象は MIT License のソースのみとする。現在の 0.1.0 を npm、Cargo、Tauri で揃え、CLI の `--version` は Cargo のパッケージバージョンから取得する。ヘルプとバージョンは文書を読む前に処理し、オプションと同名のファイルには `--` を用いる。初回のユーザー用 CLI インストールは単体実行ファイルのコピーとし、システム全体のインストーラーを導入しない。Apple Silicon に合わせて macOS のデプロイ最小値を 11.0 とするが、古い全 OS バージョンでの動作確認を意味しない。

依存物には元のライセンスが適用される。バイナリ配布用のライセンス同梱、Developer ID 署名、公証、自動公開は、バイナリ配布を計画する段階で整備する。ソース公開では既存の Git 履歴を保持し、リポジトリの公開設定変更は所有者による別の操作とする。

## 10. 依存関係の保守と CI

Dependabot で Cargo、npm、GitHub Actions を毎週確認し、メジャー更新も対象として、CI 成功後に更新ごとに人間がレビューして手動マージする。依存物ごとの差分を確認しやすいよう、当初はグループ化せず、バージョン更新 PR はエコシステムごとに最大5件までとする。

現在の対象に合わせ、macOS 15 Apple Silicon の CI ジョブを1つ設ける。OS の指定をジョブ単位に置き、Rust の作業ディレクトリを明記することで、今の Windows/Linux 対応を主張せずに後の OS 別ジョブでも検証を再利用しやすくする。リリース用スクリプトのテストが小さな Rust フィクスチャをコンパイルするため、npm テストより先に Rust を用意する。CI の Rust は意図的に更新するまで Clippy の診断を一定に保つため 1.99.0 に固定し、Node の対応範囲は重複記載せず `package.json` から読む。Tauri が利用するフロントエンド資産は Cargo の検証より先にビルドする。依存物のダウンロードをキャッシュし、古いアプリ成果物を残さないよう成果物は再構築する。GitHub 公式 Action を完全なコミット SHA で固定し、ワークフローは読み取り権限のみで動作させ、通常の PR と Dependabot PR がシークレットなしで同じ検証を使用する。運用手順と所有者側の設定は [RELEASING.md](RELEASING.md) を参照する。

## 11. 実装前に確認する小さな論点

- `mjp` の配布名としての使用可否は、公開前に GitHub/Homebrew/crates.io/npm/PyPI/一般 Web・商標で確認する。名称変更だけで各レジストリの利用可能性を保証しない。
- Windows/Linuxは設計対象だがPhase 1の検証対象はmacOS Apple Silicon。WindowsのGUI実行ファイルでは呼び出し元コンソールへのテキスト出力に制約があることが[Tauri CLI plugin](https://v2.tauri.app/plugin/cli/)に記されている。WindowsでのCLIエラー表示と`Ctrl+W`は移植時に実機確認する。また、Windowsの本番ビルドではアプリのURLが`http://tauri.localhost`になるため、現在`tauri:`スキームのみを許可している`on_navigation`が初期ページの読み込みを拒否しないか確認する。
- 相対ファイルリンクと外部画像への対応は後続段階とする。ローカルのラスター画像は、前述の範囲を限定した読込処理で扱う。
